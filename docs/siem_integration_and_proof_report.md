### Genuine Gaps Identified in Part A (Reported Without Altering Core Warrant Record Generation)

1. **Rejected Inbound HTTP Scanner Intakes (`not found` in PostgreSQL at `d80601a`):** Accepted scanner findings (`remediation_traces`) and upstream feed poll attempts (`feed_sync_runs`, including `FAILED` syncs) are persisted in PostgreSQL, whereas **rejected push intakes** (`HTTP 401` invalid `X-Warrant-Intake-Token`, `HTTP 413` oversized body, or malformed XML/JSON rejected inside zero-egress `warrant-extractor`) are returned synchronously on the HTTP response without writing a dedicated `ingest_events` database row tracking `records_received` vs. `records_rejected`.
2. **Unbound `WN-7` Finder Shield-Arm Trace Asymmetry (`code-read`):** When an unmapped or unbound `WN-7` vulnerability (`warrant_id == ""`) arms a Storm Shelter bridge, `containment_bridges` is immediately created/updated with `armed_at`, `substrate_family`, and `manifest_yaml`, but `AppendRemediationTrace` is only called on bound remediation pipelines. The SIEM shipper therefore streams **both** `containment_bridges` / `admission_lockouts` / `drift_incidents` and `remediation_traces` under `SHIELD_EVENT` so zero shield arm/disarm events are missed.
3. **Timestamp vs. Sequence Ordering on Non-Ledger State Tables (`code-read`):** Core WORM ledger tables carry strict `BIGSERIAL seq_no` columns, whereas operational state tables (`deployment_orders`, `deployment_results`, `containment_bridges`, `shadow_runs`, `feed_sync_runs`) previously lacked an explicit integer sequence column; `internal/db/siem.go` derives a deterministic monotonic microsecond cursor (`EXTRACT(EPOCH FROM ts)*1e6`) paired with stable tie-breaking so every stream ships in deterministic chronological order without modifying core Warrant tables.

## Part B — 13 Named SIEM Senders, Ordered Outbox Shipper & UI Configuration

### 1. Shared Ordered Shipping Path (`internal/db/siem.go` & `internal/adapters/siem/shipper.go`)
- **Single Shipping Engine, 13 Thin Vendor Senders:** All 13 SIEM senders implement `SIEMSender` on top of one shared PostgreSQL cursor shipper (`siem_stream_cursors`).
- **Strict Monotonic Ordering (Zero Reordering):** `FetchOrderedSIEMStreamBatch` queries each subscribed Warrant table in strict `ORDER BY seq_no ASC` (or timestamp-micros `ASC`), shipping batches sequentially and advancing `last_acked_seq` **only after** the target SIEM acknowledges the batch (`2xx` HTTP / `HEC code:0` / `_bulk errors:false` / TCP write completion).
- **Lossless Queue & Retry on Outage:** When a SIEM destination is unreachable or returns an error, `last_acked_seq` does **not** advance; unshipped records remain queued in PostgreSQL (`queued_count`), `failed_count` and `retry_count` increment with bounded exponential backoff (`next_attempt_at`), and `last_error` surfaces immediately in the operator-selected Warrant Console views (`SIEMViewStatusStrip.tsx`).
- **Credential Reference Only (`internal/adapters/siem/credref.go`):** Both the React UI (`SIEMDestinationsModal.tsx`), the HTTP API (`rejectRawSecretFieldsInSIEMPayload` + `ParseAndValidateCredentialRef`), and PostgreSQL (`CHECK` constraint on `siem_destinations.credential_ref`) accept **only** secret reference URIs (`env://VAR`, `file:///run/secrets/...`, `k8s-secret://...`, `aws-sm://...`, `azure-kv://...`, `gcp-sm://...`, or `none://`). Raw tokens, `Bearer`/`Splunk` headers, and PEM blocks are rejected (`HTTP 400`). `env://` references resolve directly from Warrant's `/proc/self/environ`-scrubbed `envseal` memory vault.
- **Zero Dual-Key & Zero Extra Device Step (`VerifySIEMConfigAuth`):** Creating, editing, toggling, flushing, and deleting SIEM destinations require only the active Warrant Console operator session (no `2-of-2` dual key and no extra hardware WebAuthn prompt). Every SIEM configuration change is sealed into WORM hash-chained table `siem_config_audit` (`trg_worm_siem_config_audit`) and verified by `VerifyAllLedgerChains`.
